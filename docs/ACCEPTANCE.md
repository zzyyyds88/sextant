# 验收流程

这份文档规定的不是"跑一遍接口看看有没有报错"，而是**怎样才算这个能力真的能用**。
`sextant acceptance` 和 `sextant journey` 都按这里写的规则判定；两者不能自相矛盾。

## 0. 为什么要有这份文档

这套代码里真实发生过下面这些"看起来正常、实际是坏的"：

| 现象 | 实际发生的事 |
|---|---|
| `--clear` 返回 `ok:true` | 空文本的 base64 是空串，`--arg` 被 shell 吞掉，provider 回 `No value for argument`，**输入框从来没被清空过** |
| 类型为 `ime.Restore` 的函数存在且有单测 | 生产代码里**零调用**，用户的默认输入法被换掉后再也没回来 |
| `global home` 返回 200 | 把 `GLOBAL_ACTION_HOME=2` 当 KeyEvent 码发出去，实际按的是 `KEYCODE_MOVE_END`（2），**什么都没发生** |
| `apps/launch` 返回 200 | 这台 ROM 上 `/system/bin/monkey` 是没有 shebang 的脚本，`exec` 直接 `exec format error` |
| 微信 `tree` 返回 420 个节点 | 那是微信自己的浮窗/小程序窗口，主界面才是真的（1 个空节点） |

所以"接口通了"和"功能对了"是两件事，必须分开验证。

## 1. 三条规则

一个能力算 PASS，必须**三条同时成立**：

1. **像用户那样操作** —— 走公开 API，走用户会走的路径（点会话、输入、发送、锁屏），
   不直接改内部状态、不跳过前置步骤。
2. **用另一条通道复核** —— 结论不能由"造成这个结果的那条通道"自己给出：
   - 用 a11y 树输入 → 用 OCR（像素）复核；
   - 写设置 → 立刻读回来比对，再改回原值；
   - 锁屏 → 问 keyguard 状态，不看锁屏接口自己的返回值；
   - 截图 → 通过另一个端点把文件下载下来，比对字节数与 PNG magic。
3. **读审计日志，确认预期的那条代码路径真的跑了** —— 两种实现可能产生同样的可见结果，
   只有日志能说清是哪一种跑的。日志里没有预期那行，就是 FAIL，即使界面看起来对。

三条有任何一条不成立 → **FAIL**，并且把"观察到的"和"日志里缺的"都写进报告。

## 2. 硬性约定

- **不许把跳过算通过。** 无法执行就 SKIP 并写明原因；SKIP 永远不计入 PASS。
- **不许留下副作用。** 改过的设置要改回去（`journey` 的 settings 步骤自己会还原），
  claim 的会话要释放，创建的文件要删掉，创建的触发器要删掉。
- **不许用 sleep 当同步。** 等的是**条件**（某个 resource id 出现），不是时间。
  写死的 sleep 会让问题变成"偶尔失败"，而不是"稳定暴露"。
- **失败要带原文。** 报告里放守护自己的错误字符串，不要改写成模糊的"失败"。
- **每个 PASS 都要有可复核的证据串**：节点数/文本数、OCR 行数、字节数、设置的前后值、
  日志那一行的原文。

## 3. 两层验收

### 3.1 能力矩阵 `sextant acceptance`

回答"每个端点在真机上能不能应答、返回的东西是否自洽"。41 项，覆盖感知、输入、会话、
系统、显示、WebRTC、触发器、锁、通知流等。能力被 ROM 限制或缺真机样本时如实 SKIP
（例如验证页分类），SKIP 不计入 PASS。

### 3.2 使用流程 `sextant journey`

回答"一个用户能不能真的用它把事做完"。21 步，每步都按第 1 节的三条规则判定。

```bash
sextant journey --out out/journey-$(date +%Y%m%d-%H%M%S)
```

它做的事，按场景：

| 场景 | 步骤 | 独立复核 | 日志要确认 |
|---|---|---|---|
| wechat | 启动微信 | 前台 component 是微信，且树里 ≥50 节点 / ≥5 条文字（1 节点 0 文字＝空根节点，说明兼容服务没生效） | `apps: launch …` |
| wechat | 打开一个会话 | 等会话行 `id/kbq` 出现 → find+click → 等输入框 `id/bkk` 出现 → OCR ≥3 行 → 树里能读到联系人名 | `ui: find+click`、`ui: ocr` |
| typing | 输入不发送 | 先清空，再输入唯一探针，从树里读回必须一字不差 | `input: text via …` |
| typing | 清空输入框 | 探针从树里消失 | `ime commit 0 chars` |
| typing | 输入法立刻归还 | 提交前后各读一次 `default_input_method`，**不能还是我们的** | `ime: keyboard handed back to …` |
| perception | 树 / OCR / 像素互相印证 | 三者都非空，且树里某个字符串也出现在 OCR 文本里 | `ui: ocr` |
| perception | 截图是真图 | 下载回来比对字节数 + PNG magic | `ui: screenshot` |
| settings | 改设置并生效 | 读回值 == 写入值，再改回原值并确认 | `settings: …` |
| session | 第二个写者被拒 | 第一个 claim 成功，第二个必须 409 | `session: claimed …` |
| session | 释放后设备归还 | 活跃会话数为 0 | `session: released …` |
| apps | 启动 → 观察 → 停止 | 前台真的变成目标 app | `apps: launch …`、`apps: force-stop …` |
| files | 上传 / 下载 / 删除 | 下载回来字节必须与上传完全相同 | `files: uploaded`、`files: deleted` |
| lock | 锁屏再解锁 | 锁后 keyguard=true 且屏灭；解锁后屏亮且 keyguard=false | `device: lock requested`、`unlock: …` |
| trigger | 定时器触发 | 3 秒内至少 1 次 run 记录 | `trigger: created …` |
| trigger | 删除后不再触发 | 列表里没有它 | `trigger: deleted …` |
| hud | 有人操作时叠加层出现 | `visible=true` **且** WindowManager 里真有窗口 | `session: claimed …` |
| hud | 说的是动作不是「控制中」 | 叠加层文案 `点「通讯录」`，不是空也不是「控制中」 | `ui: find+click` |
| hud | 暂停真的拦住动作 | 撑过一整轮心跳（17s）仍 `paused=true`，且 tap/text/global/key **四条**注入路径都 409 | `hud: paused=true` |
| hud | 停止释放一切并保持 | 16s 后仍无活跃会话、注入仍被拒 | `hud: stop pressed (…)` |
| hud | 新任务从干净状态开始 | 新 claim 成功、`stopped=false`、注入恢复 | `session: claimed …` |
| 输入 | 打字不切换用户的输入法 | `settings get secure default_input_method` 前后一致，日志是 `via a11y_set_text` | `input: text via a11y_set_text` |
| 输入 | 打字够快 | 单次 commit ≤ 400 ms（旧路径实测 1.4–1.6 s） | 同上 |
| 点击 | 点的是节点不是盲坐标 | 回复里有 `via: node`/`ancestor`；点微信会话行进的是聊天页，不是联系人卡片 | `ui: find+click … via node` |

## 4. 读日志的方法

日志通过**公开 API**读，不走 adb——验收对象是被测系统本身，读日志的通道不能是特权后门：

```bash
sextant get /data/adb/sextant-core/log/core.log --out /tmp/h.log
```

`journey` 内部就是这么做的：步骤开始前记下当前行数，步骤结束后只取新增行，
在新增行里找预期片段。这样"上一次运行留下的那行"不会冒充这一次的证据。

日志轮转会把文件截断到最近几百行，导致新行数小于旧行数；这种情况按"整个文件都是新的"处理，
再在尾部找断言，而不是当成"没有新日志"。

## 5. 手动验证清单

自动化覆盖不到的，发版前人工过一遍（每项都要给出实际观察，不接受"应该没问题"）：

- [ ] 拔掉 adb 后守护仍在跑：`sextant health` 从另一台机器可用。
- [ ] 重启一次手机，等 boot 完成后 `sextant status` 显示 `a11y OK` + `compat` 已绑定 + `bg_ok true`。
- [ ] 微信冷启动后 `sextant tree` 能读到会话列表（不是 1 个节点）。
- [ ] 用 CLI 给一个真实联系人发一条消息，肉眼确认对方会话里出现。
- [ ] 打字结束后，手机上自己的键盘能正常弹出（不是我们的隐形输入法）。
- [ ] HUD 悬浮条在受控期间显示、暂停/停止可用，停止后所有会话被释放。
- [ ] 卸载模块后：a11y 设置、默认输入法、亮度/超时都回到安装前的值。

## 5.1 HUD 的判定为什么这么严

实物证据：HUD 胶囊裁切与截图对比保留在私有验收记录中。

HUD 是"有人正在操作你的手机"这句话的唯一载体，所以它的验收不看"接口返回了 ok"：

- `visible=true` 不算数，`dumpsys window` 里必须有那个窗口；
- 文案不能是兜底的「控制中」，必须能读出刚做过的动作；
- 暂停必须撑过一整轮心跳（叠加层每 15s 心跳一次，早期实现的心跳会把暂停清掉）；
- 暂停/停止后**每一条**注入路径都要被拒，只拒新 claim 等于没拒；
- 停止后要保持，直到下一次 claim —— 心跳不能把它恢复。

## 5.2 输入与点击的判定

- **输入法不许动。** 这是用户明确要求过的（「只有 agent 需要打字的时候才使用，打完字切换回去」），而更好的做法是**根本不用切**：`a11y_set_text` 直接写字段。验收时必须前后读一次 `default_input_method` 比对，不能只看日志里写了什么。
- **点击要说是怎么点中的。** 回复里的 `via` 字段是唯一能区分「节点点中了」和「盲目点了个坐标、恰好没事」的地方；后者在浮窗、遮罩、列表复用的情况下会点错且不报错。

## 6. 已知未覆盖

诚实列出来，避免"PASS 30"被读成"全都验过了"：

- **HUD 视觉**：`hud` 相关接口有测，但"悬浮条画得对不对"只能人眼看。
- **WebRTC 观感**：只验证了 RTP 包数与字节数，画面延迟/花屏靠人工看。
- **短信发送**：只验证请求被接受与状态可查，不真的往陌生号码发短信。
- **解锁图案**：用真实凭据验证过，但**忘记图案**这一分支无法安全演练。
- **微信白名单**：依赖微信当前版本的服务名白名单，升级后需按 `docs/DESIGN.md` §9.3 复验。
- **多用户 / 分身**：只测了 user 0。
